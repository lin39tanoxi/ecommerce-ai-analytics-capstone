# 服务与数据表对应清单

> 状态：总体设计定稿。以下是本项目从零实现时拟定的表名、字段和归属，不表示 `FuQingGuan/gmall` 仓库的原始数据库结构。商城与问数系统独立开发和部署；问数系统不拥有商城业务数据，但运行时依赖商城 MySQL 只读副本。

## 1. 商城服务与数据归属

约定：每个业务服务只写自己的 MySQL schema；各 schema 在同一个 MySQL 主库实例上，以便复制到一台只读副本并在副本上跨 schema 查询。其他商城服务仍通过接口或业务事件获取所需信息，不借此进行跨服务直连。跨库的 `member_id`、`sku_id`、`order_id` 等仅作为业务关联标识，不建立跨服务物理外键。Redis 和 Elasticsearch 中的数据可以从业务数据重建。若将业务 schema 拆到不同 MySQL 实例，单一普通副本不再覆盖全部业务数据，须另行设计 CDC 汇聚方案。

| 服务或组件 | 自有存储 | 核心表、索引或键 | 负责的数据与业务 | 问数可访问范围 |
| --- | --- | --- | --- | --- |
| API 网关 Gateway | 无业务库 | 无 | 统一入口、路由、身份校验、限流入口 | 否 |
| 认证服务 Auth | Redis | `auth:token:{tokenId}` 等登录状态键 | 顾客与管理员登录、令牌；身份资料分别由会员服务和后台管理服务持有 | 否 |
| 会员服务 UMS | `mall_ums` | `ums_member`、`ums_member_address`、`ums_member_favorite` | 会员账号、收货地址、收藏 | 通过脱敏会员视图访问分析字段；不直查会员、地址等敏感基表 |
| 商品服务 PMS | `mall_pms` | `pms_category`、`pms_brand`、`pms_spu`、`pms_sku`、`pms_sku_image`、`pms_sku_attribute` | 分类、品牌、商品与 SKU、上架状态、标价 | 可直查获准商品表的非敏感列，也可使用商品语义视图 |
| 搜索服务 Search | Elasticsearch | `product_sku` 索引 | 商品关键词、分类和筛选检索；索引由商品变更事件更新 | 否，商品维度以 PMS 数据为准 |
| 购物车服务 Cart | Redis | `cart:{memberId}` | 购物车商品、数量和勾选状态；下单时由订单服务保存商品快照 | 否，成交明细以 OMS 为准 |
| 营销与秒杀服务 SMS | `mall_sms`、Redis | `sms_coupon`、`sms_coupon_rule`、`sms_coupon_claim`、`sms_activity`、`sms_flash_sale_item`；秒杀限购键 | 优惠券领取与核销、活动规则、秒杀商品与限购 | 可直查活动、规则表的非敏感列；会员领券关系经脱敏视图访问 |
| 库存服务 WMS | `mall_wms` | `wms_warehouse`、`wms_stock`、`wms_stock_reservation`、`wms_stock_change` | 仓库、SKU 库存、预占、确认扣减、超时释放与退货回补 | 可直查库存、变动表的非敏感列；销售额不直接用库存计算 |
| 订单与售后服务 OMS | `mall_oms` | `oms_order`、`oms_order_item`、`oms_order_status_log`、`oms_refund_request`、`oms_refund_item`、`oms_shipment` | 下单、商品价格快照、订单状态、发货、取消、退款申请及审核 | 可直查订单明细、状态等获准列；含会员关联的订单和售后数据优先经脱敏视图访问 |
| 支付服务 Payment | `mall_payment` | `pay_payment`、`pay_refund`、`pay_notify_log` | 模拟支付、实际支付流水、退款流水及通知幂等 | 可直查支付、退款表的获准列；成功流水指标使用语义视图 |
| 后台管理与内容服务 Admin | `mall_admin` | `sys_admin_user`、`sys_role`、`sys_permission`、`sys_user_role`、`cms_banner`、`cms_notice` | 后台账号与权限、轮播图、公告；通过业务服务管理商品/订单等 | 否 |

MySQL 主库和只读副本属于数据基础设施，不是新的业务微服务。主库部署在商城侧，专用只读副本作为独立 MySQL 实例部署在问数侧；两者分别持久化运行。主库的业务 schema 和 `mall_reporting` 报表视图 schema 持续异步复制到副本；问数系统只在副本执行查询，不调用商城微服务，也不写入业务 schema。`mall_admin` 等 schema 即使物理上存在于副本，问数账号也没有访问权限。该副本用于分析查询，不承担商城主库自动故障切换职责。

Nacos、Sentinel、Zipkin、Seata、RabbitMQ 和 Nginx 是基础设施，不拥有上述业务表。RabbitMQ 承载商品变更、订单、支付与退款等事件；事件应包含唯一 `event_id`，消费者按事件编号和业务单号幂等处理。

## 2. 下单到退款的关键表

下表列的是总体设计阶段需要先固定的字段。实现时可以补充审计字段、索引和约束，但不应改变订单、支付和退款的归属关系。

| 表 | 主键与关键关联 | 关键字段 | 何时写入或更新 |
| --- | --- | --- | --- |
| `pms_sku` | `sku_id`，关联 `spu_id`、`category_id` | `sku_name`、`list_price`、`sale_status` | 商品上架或改价；订单保存当时的名称和价格快照 |
| `wms_stock` | `warehouse_id` + `sku_id` 唯一 | `available_qty`、`reserved_qty` | 预占、释放、确认扣减、退货入库时更新 |
| `wms_stock_reservation` | `reservation_id`，记录 `order_id`、`sku_id` | `qty`、`status`、`expires_at` | 下单预占；支付成功确认或超时释放 |
| `oms_order` | `order_id`，记录 `member_id` | `order_status`、`payment_status`、`refund_status`、`order_amount`、`discount_amount`、`payable_amount`、`created_at` | 创建订单、收到支付结果、取消或退款结果时更新 |
| `oms_order_item` | `order_item_id`，记录 `order_id`、`sku_id` | `sku_name_snapshot`、`unit_price_snapshot`、`qty`、`item_discount_amount`、`item_payable_amount` | 创建订单时写入，作为历史成交快照 |
| `pay_payment` | `payment_id`，记录 `order_id` | `attempt_no`、`status`、`paid_amount`、`paid_at` | 创建支付单、模拟支付成功或失败时更新；成功流水是实付金额依据 |
| `oms_refund_request` | `refund_request_id`，记录 `order_id`、`member_id` | `requested_amount`、`reason`、`review_status`、`created_at` | 顾客申请、管理员审核时更新 |
| `oms_refund_item` | `refund_request_id` + `order_item_id` | `refund_qty`、`requested_amount` | 按订单明细申请部分退款时写入 |
| `pay_refund` | `refund_id`，记录 `refund_request_id`、`payment_id` | `status`、`actual_refund_amount`、`refunded_at` | 支付服务执行退款时写入；成功流水是实际退款金额依据 |

退款申请金额与实际退款金额应分别保存；一笔订单允许多次部分退款，但成功退款累计额不得超过实际支付额。仅退款不回补库存；退货退款须在商品验收入库后记录库存回补。

## 3. 主库复制、只读副本与问数查询面

同步机制参考 MySQL 原生主从复制：主、副实例使用不同的 `server_id`，主库启用 binlog，按行记录变更（ROW）并使用 GTID 标识事务；副本以专用复制账号和 GTID 自动定位持续读取主库日志。首次建立副本须先进行一次一致性数据初始化，再开始增量追赶；这与“问数系统不定期导入业务快照”是两回事。具体配置语法以最终采用的 MySQL 版本为准。

主库将已提交事务的变更记录到 binlog，副本持续接收并应用；这不是定时导出，也不需要问数系统导入快照。新增、修改和物理删除都会传播到副本，因此副本不是历史档案。复制默认异步：副本可能短暂落后于主库；查询页结合复制监控给出数据时效提示，复制中断或延迟超出阈值时明确告警，不宣称结果绝对实时。副本不可用时问数查询应失败或暂停，不能悄悄回退查询商城主库。

部署与运维约定：为副本配置独立持久化存储、进程自动重启和健康检查；监控复制接收与应用状态、错误和延迟，并保存必要的主库 binlog 以支持短时断线后追赶。自动重启不等于高可用；若主库和副本共用一台宿主机，实验仅证明逻辑读写隔离，不能声称物理故障隔离。副本物理上保存被复制的业务数据，视图授权不等于数据已经从存储中脱敏，故应使用模拟数据并限制数据库管理员与网络访问。

问数查询面采用“获准业务表的非敏感列 + 脱敏与指标语义视图”两层设计，而不是仅允许查询固定视图。在主库建立 `mall_reporting` schema，使用跨业务 schema 的报表视图承载脱敏关联和复杂指标；视图定义随主库复制到副本，实际查询只在副本执行。问数账号在副本上仅获指定业务表非敏感列及指定视图的 `SELECT` 权限，不获敏感列、管理权限和 `INSERT` / `UPDATE` / `DELETE` 权限；副本同时启用 `read_only` 与 `super_read_only`。即使大模型生成了危险 SQL，应用层也必须拒绝非只读语句、未授权对象、超大结果集及超时查询。模型可见的表结构说明只包含已授权对象与列。问数系统自有的聊天记录、评测集和语义层配置另存自己的应用库，不与商城业务数据混写。

下表列出拟允许直接查询的业务表及列类型；实施时按最终表结构列出精确列名，逐列授权，不对整个业务 schema 授予通配 `SELECT`。涉及会员身份、收货地址、支付渠道凭据或后台账号的数据不在直接查询范围内。

| 可直查业务表 | 拟开放的非敏感列及用途 |
| --- | --- |
| `mall_pms.pms_category`、`pms_brand`、`pms_spu`、`pms_sku` | 商品标识、名称、分类、品牌、状态、标价；支持灵活商品筛选与分类分析 |
| `mall_sms.sms_activity`、`sms_coupon_rule`、`sms_flash_sale_item` | 活动标识、类型、规则、起止时间及商品关系；会员领券记录通过脱敏视图访问 |
| `mall_wms.wms_stock`、`wms_stock_change` | SKU、仓库标识、可售/预占数量、变动类型与时间；不开放内部操作人信息 |
| `mall_oms.oms_order_item`、`oms_order_status_log`、`oms_shipment` | 订单/商品标识、成交快照、状态及发货时间；不开放收货人和详细地址 |
| `mall_payment.pay_payment`、`pay_refund` | 内部订单/支付/退款标识、状态、金额及时间；不开放外部支付凭据或完整渠道流水号 |

`oms_order`、`ums_member` 等含会员关联或个人信息的表，优先通过脱敏视图开放可分析字段。需要把表 A 的获准列与表 B 的脱敏标识关联时，应提供一致的安全关联键或语义视图，不能让模型靠读取原始个人信息完成 JOIN。

| 副本上的补充语义视图 | 商城业务表来源 | 对外字段或用途 |
| --- | --- | --- |
| `mall_reporting.v_member` | `mall_ums.ums_member` | 稳定的脱敏会员标识、注册时间；不暴露姓名、手机号和详细地址 |
| `mall_reporting.v_sku` | `mall_pms.pms_sku`、`pms_spu`、`pms_category`、`pms_brand` | `sku_id`、商品名、分类、品牌、上架状态 |
| `mall_reporting.v_order` | `mall_oms.oms_order` | `order_id`、脱敏会员标识、创建时间、订单状态、应付金额 |
| `mall_reporting.v_order_item` | `mall_oms.oms_order_item` | `order_item_id`、`order_id`、`sku_id`、数量、成交价格快照和分摊优惠 |
| `mall_reporting.v_payment` | `mall_payment.pay_payment` | `payment_id`、`order_id`、成功实付金额、支付成功时间；排除失败和重复通知 |
| `mall_reporting.v_refund` | `mall_payment.pay_refund`，关联 `mall_oms.oms_refund_request`、`oms_refund_item` | `refund_id`、`order_id`、退款商品、成功退款金额和时间；多退款明细须按明确比例归属，避免连接后重复计数；排除待审核及失败退款 |
| `mall_reporting.v_promotion` | `mall_sms.sms_coupon_claim`、`sms_activity`，关联订单优惠标识 | 活动、优惠券与订单的对应关系，用于营销效果分析 |
| `mall_reporting.v_inventory` | `mall_wms.wms_stock`、`wms_stock_change` | SKU 可售库存、预占库存及库存变动；不含内部操作人信息 |
| `mall_reporting.v_shipment` | `mall_oms.oms_shipment` | 订单发货、物流状态及时间；不含详细收货地址 |
| `mall_reporting.v_sales_daily` | 成功支付、成功退款视图 | 按天统计成功实付额、成功退款额及净额 |
| `mall_reporting.v_product_sales` | 订单明细、成功支付、成功退款及商品视图 | 商品销量、成交额与退款额；支付和退款按订单明细归属 |
| `mall_reporting.v_repeat_purchase` | 订单、成功支付及会员视图 | 指定时间范围内的支付用户和复购用户 |

脱敏会员标识在相关视图中必须保持一致，以支持跨视图关联。报表视图的授权和定义须在数据库实现阶段验证，尤其避免“视图意外暴露敏感基表字段”的问题。查询覆盖范围由获准业务表列与语义视图共同决定，而非副本物理上复制了哪些表；需要新增可问业务时，先补授权列、字段语义与必要视图，再扩充评测集。

指标口径先固定为：`实付额 = 成功支付流水金额之和`；`退款额 = 成功退款流水金额之和`；`净销售额 = 统计期内实付额 − 统计期内退款额`。日期分别以支付成功时间和退款成功时间归属，因此这里的净销售额是“当期净额”，并非某批订单最终贡献额。`复购率 = 统计期内至少支付 2 笔不同订单的用户数 ÷ 至少支付 1 笔订单的用户数`。这些定义应与评测集的标准 SQL 保持一致。按商品统计金额时，支付额应依据订单明细的应付额分摊，退款额应依据退款明细归属；若存在运费，应单列运费，不计入商品销售额。

## 4. 后续设计检查点

1. 每张业务表只能指出一个负责写入的服务；跨服务引用使用业务 ID，不建跨库物理外键。
2. 订单、支付、退款分别有独立状态，且支付、退款成功事件重复投递时不会重复计数。
3. 一笔“下单 → 支付 → 部分退款”的样例能追溯到 `oms_order`、`oms_order_item`、`pay_payment`、`pay_refund`，并算出问数结果。
4. 一次新增、修改、删除订单相关记录后，验证副本最终出现相应变化；断开并恢复复制后可继续追赶，且页面能提示复制延迟。
5. 问数账号只能访问获准业务表列及语义视图，不能写副本、读敏感列或调用商城微服务；生成 SQL 的应用层校验与数据库权限同时生效。
6. 问数指标以副本已同步的数据为准；跨服务异步业务事件与数据库异步复制都可能造成短暂中间状态，评测时记录数据时间点。
7. 停止副本或制造复制错误后，问数系统应给出故障/过期提示且不能回退访问主库；分别测试副本恢复后的追赶能力与主库启用复制前后的业务写入延迟。
